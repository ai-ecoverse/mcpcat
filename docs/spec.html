mcpcat

A curl for the Model Context Protocol · spec draft 3 · 2026-10-12 · open questions resolved · repo ai-ecoverse/mcpcat · decided as “slicc-mcp” in slicc#3889, part of Sliccy Seven (#3793)

mcpcat is one command that talks to any MCP server from a shell, and turns any shell command into an MCP server. It runs natively on macOS, Linux and Windows, and inside Sliccy Seven as a kernel program, with the same flags, the same output and the same config file in both places.

mcpcat https://mcp.example.com/mcp                  # what is this server? (info + tools)
mcpcat weather get-forecast --lat 51.5 --lon -0.12  # call a tool of a configured server
mcpcat --json docs search -d '{"q":"oauth"}' | jq .structuredContent
mcpcat serve --http 8808 ./scripts/jira.jsh         # publish a CLI as an MCP server
mcpcat code -e 'return (await tools.mcp__docs__search({q:"cimd"})).length'

1. Goals and non-goals

Goals

  • Invoke. Call tools, read resources and get prompts on any MCP server, over Streamable HTTP or stdio, in one shell command, with output that pipes cleanly.
  • Discover. Tell a human or an agent what a server offers (info, tools, schemas, TypeScript declarations), search across configured servers, and turn web discovery events into candidate servers.
  • Run. Start stdio servers, keep them configured in the same mcp.json pi and slicc-agent read, and bridge them to HTTP when something else needs to reach them.
  • Expose. Publish shell commands and scripts (including .jsh) as an MCP server over stdio or HTTP, with tool schemas derived from --mcp descriptors or --help.
  • Everywhere. One codebase, one behaviour: host (Node ≥ 26 from npm) and Sliccy Seven (slicc-kernel abi: "js" program from the same npm package).
  • Agent-ready. Learnable from --help alone, deterministic JSON, stable exit codes, and a built-in skill (mcpcat help --skill).

Non-goals

  • No LLM inside mcpcat. Sampling requests are declined. The agent is the LLM; mcpcat is its hands.
  • No persistent daemon or session broker in v1 (mcpc's bridge processes). A long-lived connection is opt-in via mcpcat serve --proxy.
  • No legacy HTTP+SSE transport (2024-11-05 style /sse endpoints). pi and slicc-agent reject it too.
  • Not a replacement for slicc-agent's native MCP tools (slicc-agent#116). The agent keeps model-facing tools; mcpcat serves scripts, humans, stdio servers and publishing.
  • No public tunnel in v1 (six's https://<token>.sliccy.now/mcp); a follow-up issue after M6 (Q7).

2. Context: what exists today

2.1 SLICC six: the mcp supplemental command

Six's mcp-command.ts (1,684 lines, plus ~5,800 lines in shell/mcp/*) is a just-bash built-in in the browser:

  • add <url> <name>, list [--json], delete, invoke <name> [tool] [--timeout s] [--json] [--flag value …], search, refresh, auth, exposure <name> <mode> [--tool glob], import <file>.
  • Config in /workspace/.mcp/servers.json ({version: 1, servers: {name: {url, headers, tools, auth, exposure, toolExposure, transport}}}), tokens in the shared slicc_accounts store, a generated /workspace/.mcp/aliases/<name>.jsh per server that execs mcp invoke <name> ….
  • Schema-driven flag coercion: scalars, repeated flags into arrays, JSON for type: object, dotted paths (--params.url), unknown flags are errors. isError exits 1; a timeout exits 124 like timeout(1).
  • Its own client speaks 2026-07-28 (stateless, server/discover) and falls back to 2025-06-18; a second path wraps pi-mcp for ≤ 2025-11-25 (exploration doc).
  • HTTP only. The browser cannot spawn, so import skips command entries.
  • mcp --serve file.jsh [name=path …] publishes .jsh CLIs as one remote MCP server at https://<token>.sliccy.now/mcp (Cloudflare worker + OAuth consent). Tools per CLI: <prefix>_help, <prefix>_invoke {argv, stdin}, and one tool per command parsed from a --mcp JSON descriptor or from --help (serve-catalog.ts). Calls per CLI run one at a time under a time budget.

2.2 Seven: slicc-agent native MCP

slicc-agent#116 made Streamable HTTP servers native agent tools on @earendil-works/pi-mcp 1.1.0:

  • Config: pi's ~/.pi/agent/mcp.json (mcpServers), watched and reconciled. Refused there: stdio, SSE, !command values, literal secrets in headers or URL, and OAuth fields clientSecret, callbackPort, callbackUrl, clientRegistration.
  • ${NAME} placeholders are filled from the encrypted credential store, keyed mcp:<server>|<sha256(url)>.
  • Exposure modes codemode (default), direct, deferred, hidden; tool names mcp__<server>__<tool>; pi-codemode for scripts.
  • Known runtime constraints: pi-mcp's index pulls in node:child_process/cross-spawn (stubbed); its SSE parser uses Buffer.byteLength (monkeypatched); on the local-proxy route a silent SSE body dies after 30 s (bodyIdleMs); a server without CORS needs slicc-node, slicc-swift or the extension.

2.3 pi: pi-mcp, pi-codemode, pi mcp

  • @earendil-works/pi-mcp: SDK-free client. McpClient, StreamableHttpTransport (injectable fetch, GET stream, Last-Event-ID), StdioTransport (process-group shutdown), /oauth (PRM + AS discovery, DCR, PKCE, refresh, step-up), /testing in-memory pair. Protocol 2025-11-25 down to 2024-11-05; no 2026-07-28, no server side, no tasks, no sampling.
  • @earendil-works/pi-codemode: QuickJS-in-wasm sandbox whose only capability is calling injected tools. CodemodeSandbox (worker per run), InlineCodemodeSandbox (same thread), renderDeclarations for TypeScript tool declarations, store/load.

2.4 Prior art outside the ecosystem

  • Apify mcpc: the most complete MCP CLI today. Named sessions over a bridge daemon, @session tools-call name key:=json, --json that is strictly spec-shaped, grep across sessions, --proxy (a credential-hiding local MCP server), schema snapshots (--schema), help --skill, exit codes 1 client / 2 server / 3 network / 4 auth, and a careful rule that auto-discovered project config files never expand ${VAR}. We copy the JSON discipline, the proxy, grep, the skill and the project-file rule; we skip the daemon.
  • f/mcptools: Go, mock and proxy modes that expose shell scripts as tools. Its shell-tool idea matches six's --serve, which we keep.
  • Code mode: Cloudflare's “Code Mode” (tools as a TypeScript API, run in an isolate), Anthropic's “Code execution with MCP” (tools as files, progressive disclosure), and Earendil's “You said no MCP!” (2026-09-29) which made QuickJS codemode pi's default. mcpcat supports all three levels: JSON + shell, TypeScript declarations, and a QuickJS runner (§16).

2.6 Secrets in seven: fnox, the vault, slicc-jerk

Lars's rule (2026-10-13): secrets must never reach the LLM provider. The approved design (slicc-agent-plan/secrets-tokens-design.md rev 4, slicc-jerk-design.md draft 3) shapes what mcpcat may do with credentials:

  • Values live in the vault (vault.sliccy.ai). Kernel programs see placeholders in their environment (fnox), never values.
  • Injection: a request from a kernel program (through the proxy or ctx.fetch) that carries a placeholder in a header is forwarded to the vault, which substitutes the value if a root-owned rule allows that domain, method, path and header, then sends it through an exit. The response is scrubbed (@ai-ecoverse/slicc-scrub). Placeholders in the URL, query or body are never injected; WebSockets are refused.
  • MCP endpoints are never injected (§3.16): the agent registers every mcp.json URL with the vault, and forward refuses those hosts and paths whatever the rules say. The agent's own MCP requests go through the vault's separate mcp op instead.
  • fnox exec can hand real values to a child whose exact argv prefix is listed in /etc/slicc/secrets-policy.toml (sudo to enable). Shells and interpreters (node, jsh, python, …) are refused unless listed by exact argv. The child's stdout/stderr are scrubbed at the source.
  • OAuth tokens move to slicc-jerk (jerk <provider> get|list|create|drop). In the kernel, jerk is a relay that only ever returns placeholders; sign-ins run on the host or in bios.
  • Agent output is scrubbed over all vault values, so an echo is caught, but a transformed value is not. Programs must keep values out of argv and logs.

3. Key decisions

Each decision has an id so issues can cite it. All were accepted on 2026-10-12.

D1 · TypeScript, one package, two entries
mcpcat is TypeScript, published as @ai-ecoverse/mcpcat with an npm bin (dist/host/mcpcat.mjs, Node ≥ 26) and a slicc.commands.mcpcat entry (abi: "js", dist/kernel/mcpcat.mjs). Both are esbuild bundles of the same core over a small platform interface.
Why not Rust/WASI like curlwright: the WASI build has no TLS, and most MCP servers are HTTPS. A kernel JS program gets ctx.fetch over the kernel transport (TLS handled by the browser or local proxy), ctx.spawn for stdio servers and ctx.net.listen for serving. It also lets us reuse pi-mcp and pi-codemode directly, as slicc-agent does. Why not a plain Node script under slicc-jsh: that would make the optional node package a hard dependency, route every call through Node shims, and put mcpcat behind node/jsh, which fnox exec refuses as interpreters (§2.6); a direct abi: "js" command is resolved as mcpcat itself, so a policy can name its exact argv. Why not Rust like slicc-jerk: jerk's kernel build deliberately avoids TLS, while mcpcat must reach arbitrary HTTPS servers from the kernel; ctx.fetch gives that without rustls on wasip1.
D2 · pi's mcp.json is the config
mcpcat reads and writes ~/.pi/agent/mcp.json in pi's format, preserving unrelated content. Anything mcpcat adds is immediately visible to pi and to slicc-agent, and the slicc-cdp discovery sink never has to know about MCP (as requested from the slicc-cdp discovery thread). mcpcat's own state (caches, discovery inbox) lives elsewhere (§10) so mcp.json never gains keys the agent rejects.
D3 · pi-mcp for transports ≤ 2025-11-25, an own stateless path for 2026-07-28
One Connection interface, two implementations, chosen by probing server/discover first (the plan six's exploration doc made, and what mcpc does). The 2026-07-28 path is ported from six's shell/mcp/client.ts and maintained here (Q8: local only). Stdio in the kernel uses a ctx.spawn-backed transport implementing pi-mcp's transport interface.
D4 · One-shot, curl-shaped, stateless by default
Each invocation connects, does one thing, and disconnects (sending DELETE for a stateful HTTP session and closing stdin → SIGTERM → SIGKILL for stdio). No daemon. List results are cached on disk honouring ttlMs. A persistent upstream is opt-in with mcpcat serve --proxy.
D5 · Six-compatible serving
mcpcat serve keeps six's tool shapes (<prefix>_help, <prefix>_invoke, <prefix>_<cmd>), its --mcp descriptor and its --help parser, so every .jsh CLI that worked with mcp --serve works unchanged. The descriptor gains optional full JSON Schemas and annotations.
D6 · Code mode is pi's code mode
mcpcat code runs the same script environment as pi and slicc-agent (tools.mcp__<server>__<tool>, ALL_TOOLS, searchTools, describeTool, text, store/load) on @earendil-works/pi-codemode, so a script moves between the agent's codemode tool and a shell without edits. mcpcat describe --ts emits the declarations the agent sees.
D7 · Discovery never installs
Discovery events go to an inbox. Adding a server to mcp.json is always a separate, explicit mcpcat add, so the decision stays with the agent or user and the ARD publisher/URN check is shown, not acted on.
D8 · Loopback by default, secrets never echoed
serve binds 127.0.0.1; any other address requires --bearer. Header values, tokens and expanded ${VAR}s are scrubbed from errors, -v traces and --json output.
D10 · Placeholders in, never values out
mcpcat expands ${VAR} itself, inside header and config values, so -H 'Authorization: Bearer ${GH_TOKEN}' (single quotes) keeps the value out of argv on the host, and in seven sends the fnox placeholder for the kernel and vault to inject. mcpcat never stores a credential it did not get from the user's own host token store, never writes one to mcp.json, and in seven never holds a token at rest: no login state on the kernel file system. OAuth sign-in goes through slicc-jerk once it has an MCP provider kind (Q2).
D9 · Name and command
Repo, package and command are mcpcat (the issue's working name was “slicc-mcp”). No mcp alias by default; six's mcp is mapped in §18 and a compat shim is Q3.

4. Architecture

  • Platform interface (src/platform/types.ts): fetch, spawn({argv, env, cwd}) → {stdin, stdout, stderr, wait, kill}, listen({host, port}) → AsyncIterable<Conn>, fs (read/write/mkdir/rename for small files), env, cwd, isatty, stdin/stdout/stderr as web streams, signals, openUrl?, exit. Everything above it is platform-free and unit-tested on the host.
  • HTTP server: the kernel has no node:http, so serve ships a minimal HTTP/1.1 server over byte streams (request line, headers, Content-Length bodies, keep-alive, JSON responses; SSE only when a tool streams progress). The host uses the same code over node:net, so one implementation is tested in both places.
  • Bundling: the kernel bundle must be one file with no imports. pi-mcp's index re-exports StdioTransport (and with it node:child_process, cross-spawn): import deep paths or alias them to a stub in esbuild, as slicc-agent's pi-mcp-stdio-node-only patch does. QuickJS's quickjs.wasm (~637 KB) is read from the package directory at first use, not inlined.
  • Known pi-mcp gaps, patched locally (mirroring slicc-agent's patches.json; no upstream work, Q8): Buffer.byteLength in the SSE parser (no Buffer in a kernel JS program); 2026-07-28 support; stdio split out of the index.

5. Command-line interface

mcpcat [options] <target> [<tool> [tool-args…]]     curl form: info, or call a tool
mcpcat [options] <verb> …                             everything else

The first word that is not an option is a verb if it is one of the reserved verbs below; otherwise it is a target. A configured server whose name collides with a verb is reached with mcpcat call <name> … or mcpcat info <name>. mcpcat's own options come before the tool name; everything after the tool name belongs to the tool, except a lone --help.

5.5 Upgrade

  • mcpcat upgrade (alias update) asks https://api.github.com/repos/ai-ecoverse/mcpcat/releases/latest for the latest release and picks the assets install.sh uses: mcpcat-<version>.tgz and SHA256SUMS. --check only prints the current and the latest version. A newer release replaces the install; the same or an older one is up to date, and a development build (0.0.0) is refused, unless --force.
  • Every URL, the API base, the asset URLs and each redirect, must be https; plain http is allowed only to 127.0.0.1, ::1 or localhost, and a redirect from https to http is refused. MCPCAT_UPDATE_API_BASE replaces the API base for tests, and mcpcat prints one stderr line naming it when it is set.
  • Only an install.sh install is replaced: <data>/<version>/dist/host/mcpcat.mjs beside a <data>/current symlink, run by a launcher on PATH or in INSTALL_DIR. An npm, npx or pnpm install, a git checkout and any other layout are left alone, with the command that updates them (for example npm i -g @ai-ecoverse/mcpcat).
  • Before downloading anything, mcpcat checks that the launcher, its directory and the data directory are writable. It downloads SHA256SUMS, refuses a tarball without an entry before downloading it, checks the tarball's SHA-256, unpacks it beside the current version, and runs the unpacked mcpcat --version with the launcher's Node, which must print the release version within 30 seconds. Then it renames the new version into place, renames a new launcher over the old one, points current at it, and only then removes the old version.
  • mcpcat does not check a build provenance attestation: the GitHub release assets have none, and the npm provenance of the same tarball would need a Sigstore verifier (Fulcio chain, Rekor inclusion, SCTs, a trusted root) in the host bundle.
  • The kernel build prints mcpcat upgrade: not available in the kernel build; the kernel updates it and exits 1.

5.6 Experimental features

--experimental <feature>[,<feature>…] (also --experimental=<list>) turns on named draft features. A bare --experimental and an unknown name exit 2; there is no "enable everything". Like every mcpcat option it goes before the tool name: after it, --experimental is a tool argument. Each feature names the upstream revision it implements, and mcpcat --version --verbose lists them. A feature can change or disappear in any minor release: that is the contract of the flag, and --help says so. Without the flag, a feature's options exit 2 before mcpcat starts or contacts a server, and nothing about the feature goes on the wire.

events: the MCP Events extension (client)

Implements SEP-3415 at b0efd116faca, the Triggers & Events Working Group's design sketch in SEP form, for 2026-07-28 servers. mcpcat is the shell consumer, the way ntfy subscribe TOPIC CMD runs a command for each message.

mcpcat <target> --experimental events --list-events [--json]
mcpcat <target> --experimental events [options] --subscribe <event> [--<arg> value…] [-- cmd…]
  • Negotiation. The server must list io.modelcontextprotocol/events under capabilities.extensions in server/discover; otherwise mcpcat exits 5 without sending an events/* request. A ≤ 2025-11-25 server exits 5 too (the extension needs 2026-07-28). Every events/* request declares the extension in its io.modelcontextprotocol/clientCapabilities, and over HTTP carries Mcp-Name: <event> (events/list has none). No other request declares it.
  • --list-events follows nextCursor through every page of events/list and prints each event type's name, delivery modes, description, inputSchema and payloadSchema; --json prints {"events": […]}.
  • --subscribe <event> takes the event's arguments after its name, as schema-driven flags (§7) checked against its inputSchema, or as JSON with -d before --subscribe. Everything else, mcpcat's own options included, goes before --subscribe. An unknown event, a missing required argument, or an event with no usable delivery mode exits 2.
  • Delivery. mcpcat picks push (events/stream) when the event offers it, otherwise poll (events/poll); --delivery push|poll forces one, and exits 2 if the event does not offer it. Webhook delivery (events/subscribe) is out of scope: a shell has no callback URL. Poll honours hasMore (poll again at once) and nextPollMs, with a 1 s floor (30 s when the server gives none).
  • Output. Without a command, each EventOccurrence is one JSON line on stdout, like ntfy sub without a command; push occurrences lose only the io.modelcontextprotocol/subscriptionId key of their _meta. After --, the command runs once per event, one at a time and in order, with the same JSON line on stdin and MCPCAT_EVENT_ID, MCPCAT_EVENT_NAME and (when the occurrence carries one) MCPCAT_EVENT_CURSOR in its environment; its stdout and stderr pass through. A command that exits non-zero is named on stderr and the next event still runs; one that cannot start exits 2. Because -- introduces the command, a stdio server is given as a stdio: target or an mcp.json name.
  • Cursors. --cursor <c> (or --since <c>) starts from a cursor; with neither, the first request sends cursor: null (now). --cursor-file <path> keeps {"event", "cursor", "eventIds"} (the last 256 event ids), written to <path>.tmp and renamed: after each event, and whenever notifications/events/active, a heartbeat or a poll result moves the cursor. Nothing is written once SIGINT arrives, so an event whose command SIGINT stops is delivered again by the next run. The next run starts from the stored cursor and drops occurrences whose eventId it has seen, so a crash between an event and its cursor repeats nothing; --since now ignores the stored cursor. A null cursor is never replayed. An occurrence without a cursor (absent or null) leaves the last one in place, so a reconnect resumes from the last notifications/events/active or heartbeat position and nothing between it and the drop is skipped; repeats are dropped by eventId. --max-age <s> sends maxAgeMs with the first poll and with every events/stream. truncated: true with a cursor prints one notice on stderr. Within a run, duplicates by eventId are always dropped.
  • Liveness and reconnects. events/stream has no request timeout. Once a stream is active, mcpcat reconnects with its last cursor when it hears no event or heartbeat for this subscription (other notifications do not count) for --heartbeat-timeout <s> (default 60, twice the 30 s the SEP asks servers to keep), when the server ends the stream, or when the connection drops, waiting 0.5 s and doubling to 30 s; on stdio it first sends notifications/cancelled for the old stream. Poll retries transport failures the same way after its first success. A failure before the first notifications/events/active or poll result exits as usual (§8.3).
  • Errors. notifications/events/error prints a notice and the stream goes on. notifications/events/terminated, and a JSON-RPC error to events/stream or events/poll, end the subscription: exit 4 for Forbidden (-32024), exit 5 otherwise. A stdio server that exits ends it with exit 3.
  • Stopping. --count <n> exits 0 after n events (cancelling the stream: notifications/cancelled on stdio, an aborted request over HTTP). SIGINT cancels the same way, stops a running command with SIGTERM (SIGKILL if it is still running 2 s later), and exits 130.
  • Untrusted data. Notices and errors on stderr (including server-supplied notifications/events/error text) go through the same redactor as other client errors, so an expanded -H or config secret prints as [REDACTED]. Payloads are written with control characters escaped, and NUL is dropped from the environment variables. An agent reading them treats them as data, as with tool results.

11.1 Static credentials

11.2 OAuth on the host

  • Via @earendil-works/pi-mcp/oauth: PRM (RFC 9728) → AS metadata (RFC 8414, issuer check) → CIMD, else DCR, else configured clientId → PKCE → token, refresh, step-up on insufficient_scope. All of pi's oauth fields are honoured.
  • login is explicit. A call that hits 401 exits 4 and names the command; mcpcat never opens a browser on its own (mcpc's rule, and jerk's “never signs in silently”).

  • Token store, v1: pi's ~/.pi/agent/mcp-auth.json (0600), keyed by server name + URL, so pi mcp login and mcpcat login are interchangeable. URL-only targets use url:<origin+path>. With slicc-jerk installed, tokens live in jerk instead (Q2).

CIMD is the default when the authorization server advertises it, and DCR is the fallback. The document is static and lives in the sliccy-ai repo:

11.3 Credentials in seven

  • No sign-in inside the kernel. mcpcat login in seven exits 4 and points to the agent's MCP sign-in (Settings) or, later, jerk. mcpcat never writes tokens to the kernel file system, where the agent could read them.
  • Servers that are not in mcp.json (ad-hoc URL targets, or entries in another file): ${VAR} expands to the fnox placeholder, and the kernel/vault inject it when a rule covers that domain and header. Nothing special in mcpcat.
  • Servers in mcp.json (registered with the vault by the agent): mcpcat sends the request with no auth header to the registered URL. The kernel's forwarding hook routes an owner-bearing request to a registered MCP origin + path prefix through the vault's mcp { server, request } path. That path adds only that server's own credential, scrubs the body (S4) and the response (S1, then S3 as tool output), and audits the call as mcp with uid and agent tag (secrets design §3.16.1, accepted for Q9). So mcpcat call github … uses the credential the user entered for the agent, and mcpcat stays credential-free.
  • fnox secret placeholders in a request to a registered MCP URL are still refused (403); secret records are never injected into MCP or model URLs.
  • A vault 403 (no credential registered for that server, or a refused placeholder) maps to exit 4 with the vault's one-line reason.
  • Interim, until VAULT-1b ships §3.16.1: fnox exec -- mcpcat call <server> … with the exact argv in [exec], output scrubbed at the source (S2). It is weaker, since the real token sits in mcpcat's process; drop it once the vault path is live.

12. Serving: commands as MCP servers

mcpcat serve ./jira.jsh                               # stdio (default when stdout is not a TTY)
mcpcat serve --http 8808 gh=./gh.jsh jira=./jira.jsh  # Streamable HTTP on 127.0.0.1:8808/mcp
mcpcat serve --http 0.0.0.0:8808 --bearer '${SERVE_TOKEN}' ./ops.sh   # expanded by mcpcat, never a literal in argv
mcpcat serve --tool 'disk_usage: du -sh {path}' --tool 'uptime: uptime' --http 8809

12.1 Catalog (six-compatible)

For each command, mcpcat derives tools mechanically, never with a model:

  1. Run <cmd> --mcp. If it exits 0 with JSON {"commands": [{name, description, positionals, flags}]}, use it. mcpcat extends six's descriptor with optional inputSchema (full JSON Schema, wins over flags/positionals), outputSchema, annotations (readOnlyHint, destructiveHint, idempotentHint, openWorldHint) and stdin: true.
  2. Else parse <cmd> --help with six's parser (usage lines, COMMANDS/OPTIONS sections, one level of command groups), ported from serve-catalog.ts with its tests.
  3. Always add <prefix>_help (no input) and <prefix>_invoke ({argv: string[], stdin?: string}).

Prefix: name= if given, else the usage line's program name, else the file name without extension, sanitized to [a-z0-9_]. --tool 'name: template' declares an ad-hoc tool whose {placeholders} become required string properties; templates are split into argv, never passed to a shell.

12.2 Execution

  • Each call spawns the command once with argv from the schema mapping (positionals in order, then flags), stdin from stdin, cwd as given by --cwd (default: where serve started), env filtered (--env K/--env K=V, plus PATH, HOME, LANG).
  • Calls for one command run one at a time unless --concurrency n (six's rule).
  • --call-timeout (default 120 s): on expiry the call returns isError, the child gets SIGTERM, then SIGKILL if it is still running 5 s later. An HTTP client that disconnects mid-call aborts it the same way, and a call still queued behind another never starts.
  • Result: stdout as text (or as structuredContent when it parses as JSON and the tool declares an outputSchema), stderr appended under a stderr: marker when non-empty, exit status in _meta. A non-zero exit is isError: true. Output over --max-output (default 1 MiB) is cut in the middle.
  • Cancellation from the client kills the child.
  • Signals: a SIGHUP, SIGINT or SIGTERM while serve is still discovering its commands kills the discovery children and exits 129, 130 or 143, like the client verbs; once serving, the same signals shut the server down (in-flight children killed, token file removed) and it exits 0.

12.3 Transports

  • stdio: newline-delimited JSON-RPC; mcpcat's own logs go to stderr only. SIGTERM, SIGINT and SIGHUP stop serve even while stdin is open: in-flight calls and event sources are stopped, and it exits 143, 130 or 129.
  • HTTP: POST /mcp, JSON responses. Origin is checked against loopback (localhost, 127.0.0.1, [::1], *.localhost) when present; a missing Origin is allowed, as from seven's agent, curl and Node. --allow-origin adds origins. Host must be 127.0.0.1:<port>, localhost:<port> or *.localhost (DNS-rebinding defence) unless bound off loopback. Connection: close is honoured, and keep-alive otherwise. The server is stateless: no Mcp-Session-Id on initialize, 405 on GET and DELETE /mcp. --bearer is required off loopback. Prints the URL on stderr (and as JSON with --json) once listening. In seven it binds the kernel loopback (§17) and prints http://<port>.kernel.localhost/mcp, the form kernel programs, the page and the agent can reach; --json adds loopbackUrl (http://127.0.0.1:<port>/mcp) for raw-socket clients. mcpcat's own client in the kernel dials 127.0.0.1/localhost targets through ctx.net first and falls back to ctx.fetch when no kernel listener holds the port. Before slicc-kernel 1.91 that fallback reached the host's loopback through the transport; from 1.91 ctx.fetch sends loopback names to the kernel's own listeners and never to the transport, so a refused one exits 3 and names http://host.slicc.internal:<port>, the host's address for a kernel program.

12.4 Events (experimental)

Behind --experimental events (§5.6), serve is also an MCP Events server (SEP-3415 at b0efd116faca), on stdio and HTTP, in the host and the kernel. It does not combine with --proxy or --webmcp, and it needs no other commands. A kernel client reaches a kernel serve through mcpcat's own loopback fetch, which streams an SSE response without Content-Length as it arrives (decoding Transfer-Encoding: chunked) and closes the connection on abort.

mcpcat serve --experimental events --http 8813 --bearer '${TOKEN}' \
  --event 'ci.run: ./watch-ci.sh {repo}' \
  --webhook-allow https://hooks.example.com/mcp/
  • Event types. --event '<name>: <cmd>' (repeatable; the name is [A-Za-z0-9._-]+) declares an emit-only event type. The command is split like a stdio: target and run without a shell, with the environment and working directory of served commands (--env, --cwd). Each {placeholder} becomes a required string argument in the event's inputSchema (additionalProperties: false) and is replaced inside its argv token, so a value never adds arguments. events/list gives the template as the description, {"type": "object"} as the payload schema, and push, poll and (with --webhook-allow) webhook as delivery modes; server/discover declares io.modelcontextprotocol/events.
  • Sources. One process runs per event type and distinct arguments, started by the first subscriber and stopped (SIGTERM, then SIGKILL after 2 s) when the last one leaves, so {repo} watchers are per repository. Each stdout line is one event: a JSON object with an object data is an envelope whose data, string eventId and string timestamp are used; any other JSON object is the payload; any other line is {"line": "<text>"}. A missing eventId is the event's cursor and timestamp is when mcpcat read the line. Its stderr goes to serve's stderr. A source that exits while subscribed is restarted after 0.5 s, doubling to 30 s, back to 0.5 s after it ran 30 s, with one stderr line.
  • Cursors. <epoch>.<n>: the source's random epoch and the number of lines it has emitted. The last --event-buffer events (default 1000) are kept for replay. A cursor from another epoch (a restarted serve, a source that stopped), one older than the buffer, or one that cannot be read starts from the oldest kept event with truncated: true; maxAgeMs skips older events the same way. cursor: null starts at the head. Events are at-most-once across a source's lifetime, as the SEP says of emit-only types.
  • Push. events/stream answers with notifications/events/active (cursor, truncated), the replayed events, then live ones, each with its cursor, and a notifications/events/heartbeat with the last cursor every --event-heartbeat seconds (default 15). Every notification carries _meta["io.modelcontextprotocol/subscriptionId"], the request id. Over HTTP it is the SSE response to the POST, ended by the client's disconnect or, on shutdown, by a final {"resultType": "complete"} frame; on stdio it ends with notifications/cancelled or stdin EOF. Streams do not count against --concurrency. A stream writes one message at a time and reads what to send next from the source's buffer, so a slow or stalled subscriber holds no backlog of its own: when it falls behind the buffer, it gets a fresh notifications/events/active with truncated: true and continues from the oldest kept event.
  • Poll. events/poll returns up to maxEvents (default and cap 100) events after the cursor, without per-event cursors, with hasMore and nextPollMs from --event-poll (default 5 s). A poll holds a lease on the source for max(60 s, 3 × nextPollMs), renewed by each poll, so a polling client keeps the source and its buffer alive between polls.
  • Webhook. With --webhook-allow <prefix> (repeatable; an https URL whose path ends in /, without query or fragment) events/subscribe registers a callback URL whose normalized form (WHATWG URL: host case, default port and dot segments resolved) starts with one of the normalized prefixes, and which carries no credentials; the allowlist is the endpoint verification of the SEP, so no challenge is sent, and it is how the operator bounds SSRF (mcpcat does not resolve or pin addresses). A URL that is not https is -32602, one outside the allowlist -32027 (reason: "challenge_failed"). It needs an authenticated client: over HTTP, a serve with a bearer (the principal is the bearer); over stdio, the client that started serve; --no-auth answers -32024. The delivery.secret must be whsec_ and base64 of 24 to 64 bytes. The subscription id is sub_ and 16 hex digits of SHA-256 over principal, URL, name and arguments; at most 100 subscriptions. ttlMs is clamped to 1 s … --webhook-ttl (default 3600 s), and null or none gets the cap, never no expiry. Calling it again with the same key refreshes the TTL, replaces the secret (deliveries are signed with old and new for 5 minutes), and returns deliveryStatus; an unrefreshed subscription expires and releases its source. events/unsubscribe removes it, or answers -32023 with kind: "subscription".
  • Webhook delivery. Each event is POSTed as its EventOccurrence with cursor, one at a time in order per subscription, with webhook-id (the eventId), webhook-timestamp, webhook-signature (v1, HMAC-SHA256 over id.timestamp.body) and X-MCP-Subscription-Id, no redirects followed and a 5 s timeout. A non-2xx answer or a failure is retried after 1, 5, 30 and 120 s with a fresh timestamp and signature, then abandoned with one stderr line; 410 and 413 are not retried. Because delivery is sequential, each body's cursor is a safe watermark. Like a stream, a subscription reads from the source's buffer and keeps no queue of its own; an endpoint that falls behind it gets a signed {"type": "gap", "cursor": …} envelope (webhook-id: msg_gap_<16 hex>) and then the oldest kept event. deliveryStatus.lastError is one of connection_refused, timeout, tls_error, http_4xx, http_5xx; delivery is never suspended, and no terminated or verification envelopes are sent.
  • Errors. -32602 for a missing name, unknown, missing or non-string arguments, a bad cursor, maxAgeMs or maxEvents; -32023 for an unknown event; -32026 for events/subscribe without --webhook-allow; -32025 past the subscription limit. Over HTTP, an events/poll, stream, subscribe or unsubscribe whose Mcp-Name (Base64 sentinel decoded) is missing or differs from params.name gets 400 and -32020.

13. Proxy and bridge

mcpcat serve --proxy fs --http 8810                    # stdio server → HTTP
mcpcat serve --proxy https://mcp.sentry.dev/mcp --http 8811 --bearer "$LOCAL"   # hide OAuth tokens
mcpcat serve --proxy docs --stdio                      # HTTP server → stdio, for stdio-only clients
  • Keeps one upstream connection for its lifetime (the opt-in session of D4), reconnects on failure, refreshes tokens.
  • Forwards tools, resources and prompts; translates between the client's and the upstream's protocol versions (e.g. serve 2026-07-28 to the agent while the upstream is a 2024-11-05 stdio server).

14. WebMCP bridge

Requested by the slicc-cdp discovery work (the slicc-cdp discovery thread, slicc-cdp#93). Pages register tools with document.modelContext; playwright-cli webmcp-list and webmcp-call <name> <json|-> reach them over CDP. mcpcat turns a tab into an MCP server so non-browser agents can call page tools:

mcpcat serve --webmcp --tab 3 --http 8812
  • One tab for the server's life. Without --tab, mcpcat runs playwright-cli tab-list once at startup and takes the current tab (or the only one); when there is none it exits 3 and asks for --tab. Every webmcp-list and webmcp-call then carries --tab <id>, so another playwright-cli command changing the current tab does not move the server.
  • tools/list runs playwright-cli webmcp-list --json --tab <id> (cached for --webmcp-ttl, default 5 s, since pages change tools on navigation); tools/call lists again, uncached, then runs webmcp-call <name> - --tab <id> with the arguments on stdin and returns its string as text.
  • Live tool updates. With playwright-cli 1.40.0 or newer (slicc-cdp#163) the polyfill holder prints a tools-changed line (tab, target, frameId, loaderId, origin, tools in the webmcp-list --json shape) whenever a frame's list changes after ready or document-ready; a frame admitted later starts from [], and a change pending across a navigation is dropped. mcpcat then keeps the holder running even when the browser has native WebMCP, and each event replaces that frame's tools in the cached list (keyed by frameId; a list without frameId belongs to the top frame). A top-frame event for another loaderId than the holder's last ready or document-ready is ignored. A frame whose origin differs from the tab's (read once per document from tab-list) counts only when --webmcp-from-origin names it, and consequential tools stay hidden as below. A webmcp-list that finishes supersedes the events that arrived before it started; a document-ready drops the cache and the events, so the next tools/list lists again. Each applied event and each document-ready sends notifications/tools/list_changed: on stdio to a client that sent initialize, and with _meta["io.modelcontextprotocol/subscriptionId"] to each 2026-07-28 subscriptions/listen asking for toolsListChanged (acknowledged with notifications/subscriptions/acknowledged, ended by notifications/cancelled); over HTTP on a GET /mcp event stream (≤ 2025-11-25) and on the event stream a subscriptions/listen POST opens, which ends with a complete result when serve shuts down. initialize and server/discover then say listChanged: true. With an older playwright-cli nothing changes: listChanged stays false, GET is 405, subscriptions/listen is unknown, and the cache lives for --webmcp-ttl, which stays the fallback in both cases.
  • --max-output caps a call's stdout and stderr while they are read, as for commands (head and tail kept, the middle cut). The tool list is read up to the larger of --max-output and 1 MiB; a longer list is an error, not a truncated parse.
  • Annotation mapping: every tool gets openWorldHint: true and its result is wrapped as untrusted page content; readOnlyHint and untrustedContentHint pass through; consequentialHint passes through and adds destructiveHint: true, and such tools are hidden unless --allow-consequential. playwright-cli's policy (allowed, or unknown for a top-level tool from a page-defined modelContext whose tools permission policy playwright-cli cannot read) passes through as the policy annotation, and a tool listed while the polyfill arrived after the page loaded gets late: true; neither changes the wrapping, the consequential gate or --max-output. Human tools output shows the hints as [read-only, untrusted, consequential, policy: allowed, late].
  • Polyfill when the browser lacks WebMCP. With --webmcp-polyfill auto (the default) mcpcat runs playwright-cli --cdp <url> webmcp-polyfill --tab <id> (slicc-cdp 1.32.0 or newer; an older playwright-cli gets one warning and no polyfill) in the foreground for the life of serve, with its stdin a pipe that stays open: closing it is how mcpcat stops the holder on shutdown. The first tools/list waits for the holder's ready event (at most 20 s); a ready with mode: "native" means the browser has WebMCP, so with playwright-cli older than 1.40.0 mcpcat closes the holder and does not restart it (newer ones keep it for live updates). Each document-ready event (a navigation) drops the cached tool list. A holder that exits otherwise is restarted, after 0.5 s doubling to 30 s; the delay drops back to 0.5 s only once a holder has stayed up 30 s after its ready, and its stderr goes to serve's stderr. --webmcp-polyfill off never starts it. --webmcp-reload passes --reload on the first start only: it reloads the user's tab, so it is opt-in; without it a page that checked for WebMCP at load registers nothing until it reloads. --webmcp-from-origin <origin> (repeatable) passes --from-origin to webmcp-list and webmcp-call, so tools a cross-origin frame exposes to the page are listed with the origin prefix below. All playwright-cli commands run with the same environment and working directory, so they share its saved session.
  • Hints for an empty tab. When the page lists no tools, tools/list carries a hint under _meta["io.mcpcat/hint"], serve prints it on stderr at startup, and mcpcat tools prints it on stderr (hint in --json): reload the tab or use --webmcp-reload when the polyfill arrived late, or WebMCP is not enabled and --webmcp-polyfill is off. playwright-cli 1.32.0 exits 2 when document.modelContext is absent; mcpcat serves that as an empty list with the hint.
  • A tool that throws returns isError with whatever webmcp-call printed. playwright-cli (slicc-cdp v1.30.22) runs document.modelContext.executeTool, which Chrome 155 rejects with a generic UnknownError: Tool was executed but the invocation failed, so the page's own message is lost there. CDP's WebMCP.toolResponded does carry it, as exception.description (errorText is empty); it reaches mcpcat once webmcp-call invokes tools with WebMCP.invokeTool.
  • Origin is part of each tool's description; tools from more than one origin get the origin's host as a prefix (bank_example_com__lookup).
  • No cross-origin calls. webmcp-call takes only the base name and runs the first page tool with it; playwright-cli (slicc-cdp v1.25.1) cannot select by origin or frame; slicc-cdp 1.32.0 adds --frame, which mcpcat does not use yet. So a name that more than one listed tool uses (two origins, two frames, or two prefixed names that collide) is left out of tools/list, and a call to it, including one listed before another origin registered the name, is refused with a JSON-RPC error naming the origins. mcpcat never guesses which one runs. A tool registered in the milliseconds between that fresh list and the call is not seen; closing that gap needs playwright-cli to select by origin.
  • Errors name the cause. A hidden consequential tool is listed under _meta["io.mcpcat/hidden"] of tools/list, and calling it says it exists but is hidden and that --allow-consequential shows it; mcpcat call with flags says the same, exit 2. An empty list from a tab that tab-list no longer shows is a JSON-RPC error (tab <id> is gone), never an empty list. With a CDP URL (--cdp or SLICC_CDP_URL) mcpcat keeps a session on the tab and watches Page.javascriptDialogOpening: a call or list blocked by an alert, confirm or prompt stops at once with tab <id> is blocked by a JavaScript … dialog, and later lists and calls report it until the dialog closes; a tab that never answers Page.enable adds a dialog hint to the timeout. server/discover, initialize and ping never wait on the page. Without --playwright-cli, mcpcat looks for the binary in each PATH entry and exits 3 when none has it. A busy --http port prints one line and exits 3 in every serve mode.
  • Answering dialogs a tool opens. --webmcp-dialog report (the default) only reports a dialog, as above. With dismiss or accept mcpcat runs playwright-cli --cdp <url> dialog-hold --tab <id> (slicc-cdp 1.39.0 or newer; an older playwright-cli gets one warning and mcpcat reports dialogs instead) in the foreground for the life of serve, one holder for the pinned tab, with its stdin a pipe that stays open. Every tools/call first waits for the holder's ready event (at most 20 s). A dialog-opened event that arrives while a webmcp-call runs is answered with one NDJSON request, {"id","dialogId","command":"dialog-dismiss"} or "dialog-accept", never with promptText; mcpcat sends one request at a time and waits at most 7 s for its reply, and the call then returns its result. accept confirms on the user's behalf, so serve refuses it (exit 2) without --allow-consequential. A dialog the holder never announced, such as one open before it attached, one it refuses, one it did not answer in time and one that opened outside a call, stays reported as blocked. A holder that exits is restarted with the polyfill holder's backoff; a tools/call that arrives during the backoff waits for the new holder's ready (at most 20 s per holder generation) before it runs. Once two holders in a row exit without ready, or the next restart is due later than that wait, calls stop waiting and dialogs are reported as blocked until a holder is ready again. No dialog message, URL or prompt text reaches serve's output, logs or errors.
  • Depends on slicc-cdp#93 shipping --json output for webmcp-list.

19. Security model

  • mcpcat runs what you configure. A stdio server is code with your privileges; a project .pi/mcp.json could name any command. Project files are read but their command entries are not started, and their ${VAR}/!command not expanded, without --trust-project or an explicit file:name target.
  • Secrets come from the environment, the token store or !command; they are never written into mcp.json by add (a literal Bearer … value is refused with advice to use ${VAR}, matching the agent's rule) and are redacted everywhere mcpcat prints: each whole header value, its ${VAR} template and, inside it, every ${VAR} value of 8 or more characters (shorter parts would redact noise), longest first.
  • Server-supplied text in human-readable messages (error lines, the 401/403 reason, JSON-RPC and tool errors, progress, prompts, -v traces, serve logs) has C0/C1 control characters other than \n and \t shown as \xNN, after redaction, so a server cannot drive the terminal. An unanswered input request is printed as JSON with them as \u00NN escapes. Machine output (--json, results on stdout) is byte-exact.
  • serve binds loopback, checks Origin (DNS-rebinding defence from the Streamable HTTP spec), requires --bearer off loopback, and passes only an allow-listed environment to children. Tools have no shell unless the command itself is a shell.
  • proxy never leaks upstream credentials; it does not make an unsafe upstream safe.
  • Discovery stages, never installs (D7); ARD URN/publisher mismatches are shown as warnings next to the candidate.
  • WebMCP hides consequential tools by default, marks untrusted page content, stays on the tab it started on, and refuses tool names that more than one origin uses, so arguments meant for one origin never reach another.
  • Secrets never reach the model provider. When the agent runs mcpcat, its output is scrubbed by the agent, but only for untransformed values. So mcpcat keeps values out of argv (D10), never prints headers or tokens (even with -v), passes only allow-listed env to served children, and in serve never forwards the caller's Authorization to the command.
  • Code mode scripts can call tools and nothing else (no fetch, fs, timers), unless --allow-shell.

    • a byte-identical rebuild from the tag (deterministic esbuild);
    • no install scripts, and a tight files list;
    • engines minimums that are true;
    • no runtime deps, or exact pins only;
    • no Math.random for anything secret, and no network or disk I/O at import.
  2. Kernel lockdown: runs on the current certified kernel (≥ 1.64.2) using only ctx.*, never needs a withheld global, and a too-old kernel gets a clean error.
  3. Host/kernel parity, golden: the same --help, JSON output and exit codes on Node ≥ 26 and in the kernel, against the fixture servers:

    • HTTP/SSE via ctx.fetch through the kernel proxy;
    • all three protocol families, resources, prompts and elicitation;
    • serve reachable on http://<port>.kernel.localhost from another kernel program.
  4. Secrets:
    • no credential at rest on the kernel file system;
    • placeholders pass through untouched;
    • a planted marker value never appears in stdout, stderr, logs, files, mcp.json or argv;
    • ${VAR} in -H is redacted;
    • 401/403 → exit 4 with the vault's reason;
    • the host token store is 0600, and nothing is written outside it.
  5. serve and proxy:
    • loopback only by default, and the --bearer and Origin checks hold;
    • proxy mode hides credentials;
    • SIGINT/SIGTERM shut down cleanly with no orphaned stdio children;
    • memory stays steady over a long run, and reconnects work.
  6. Code mode: scripts run in the QuickJS wasm VM only (§16).
  7. Users (once enforcement ships): config paths obey DAC as cone and as scoop, and no user can read another user's mcp.json.
  8. bios's real setup: installed through the catalog path (PATH, PNPM_HOME), with a smoke test.
  9. Host: npm i -g on Node 26, and exit codes pass through.

Q1 · Agent access to MCP servers on the kernel loopback · agreed with slicc-agent
Required from slicc-agent. An mcp.json URL such as http://8810.kernel.localhost/mcp must work as an agent MCP server, so mcpcat serve --proxy makes stdio servers usable by the agent in seven. M7's add --bridge depends on it. slicc-agent routes every http(s)://<port>.kernel.localhost/… request to the kernel client's loopbackFetch({ port }). Wire shape: no Origin, Host: <port>.kernel.localhost, one request per connection with Connection: close, Content-Length bodies, and JSON or SSE responses with no CORS. Revised after homescoop's cert (2026-10-13): every kernel process and user can reach a kernel-loopback server, so bridges are authenticated by default. add --bridge generates a random token, holds it in the bridge's memory, and seals it into the vault through /dev/sealed (the reply carries only a placeholder). It writes "headers": {"Authorization": "Bearer ${MCP_<NAME>_TOKEN}"}, which the agent's vault mcp path fills in. The value is never printed, logged or written to a file; with no vault, add --bridge exits 4. The seal is {"op":"seal","kind":"mcp","name","value","server","url"} (secrets design §3.16.3): an mcp/process record bound to that kernel-loopback URL, rotatable only by the uid that sealed it. In the kernel, a serve/--proxy without a bridge entry needs --bearer '${VAR}' or --no-auth, and a generated token is never printed there, even on a TTY (the agent's bash runs in a pty). On the host it is printed once to a TTY, and otherwise written to a 0600 file whose path is printed. --no-auth opts out with a warning. HTTP serve likewise generates a bearer when none is given, a present Origin must equal the server's own origin, and POSTs must be application/json. There is no OAuth on kernel-loopback URLs (§12.3).
